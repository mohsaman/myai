Models — 87 GB on disk, one resident at a time
ModelSize ActiveWhat it is for
qwen3:30b-a3b default 18.6 GB3B General chat, reasoning, tool use. A mixture-of-experts: 30B parameters stored, only 3B activated per token — which is why it is fast, and why it reasons like a much smaller model.
qwen3.6:27b 17.8 GB27B Dense, so every parameter fires on every token — roughly 9× the compute of the default for the same footprint. Slower, markedly stronger. KV cache costs 138 KiB/token against the default's 51.
aya-expanse:32b 19.8 GB32B Composes in Persian and other non-English rather than translating into it. No reasoning block, so ~25× fewer tokens for the same answer.
gpt-oss:20b 13.8 GB21B Long-context reading, 128k window. The better talker and the worse agent — it invents tools that do not exist, so not for agentic loops.
qwen2.5-coder:14b 9.0 GB15B Writing and reviewing code.
qwen2.5vl:7b 6.0 GB8B Vision. Screenshots, diagrams, tables, scanned documents — about 8s per image.
qwen2.5:3b 1.9 GB3B Instant factual answers, and the task model that titles chats in the background.
nomic-embed-text 0.3 GB137M Embeddings for retrieval. Hidden from the model picker — it is infrastructure, not something to chat with.
Presets are not models. Telecom Expert and Qwen3 Explorer in the picker are system prompts layered over a base model, not separate weights — which is why they cost nothing extra on disk and switch instantly. What they change is framing and tool access, not capability: a preset makes a model sound like a domain expert well before it makes it right.

Chats, prompts, filesnever leave Inference, speech, images, embeddings and retrieval are all local.
The memory budget is the real constraint. 32 GB machine, ~24 GB usable by the GPU. Weights plus KV cache must fit inside that or inference silently spills to the CPU — and ollama ps still reports 100% GPU while it happens, so the only symptom is a collapse in throughput. At 48k context a 30B MoE sits at ~21 GB, leaving room for a browser and an image backend. Per-token KV cost is not a function of parameter count: check block_count, head_count_kv and key/value length before assuming a similar model behaves similarly.

Ollama

Serves the language models below. Its context window is sized from a measured KV cost, not a derived one. q8_0 KV cache, flash attention. Swapping model costs a reload — 24 GB of GPU memory holds one at a time.
ComfyUI + Qwen-Image-2.1
127.0.0.1:8188
Image generation on the GPU. 16.1 GB in three parts — diffusion model, text encoder, VAE — native 2K, and legible text inside the picture. A diffusion model: the chat model reads images, this one draws them. Research licence, non-commercial.

qwen3.8:27b-mlx the model 18.2 GB27B The one you talk to. Dense, so every parameter fires on every token, and the only one here doing vision and tools — so chat, images, code and tool use are all the same model. Apple Silicon build. Its KV cache measures 98 KiB/token, which caps context at 40k — measured, because the architecture implies 34 and that would not have fit.
nomic-embed-text 0.3 GB137M Embeddings for retrieval. Hidden from the model picker — it is infrastructure, not something to chat with.
One model, not a menu. The picker shows a single entry. Chat, code, vision and tool use are the same weights, so changing subject costs nothing — there is no second model to swap in, and no reload. Background work that used to need a small second model, writing chat titles and tags, now runs on this one too: that removes 1.9 GB from memory rather than adding to it, because nothing has to sit resident beside it. The embedding model is the one genuine exception — turning text into vectors is not something a chat model does — so it stays, hidden from the picker as infrastructure. Presets like Telecom Expert are system prompts over the same weights: they change framing and tool access, not capability, and cost nothing on disk.

Chats, prompts, filesnever leave Inference, speech, images, embeddings and retrieval are all local.
The memory budget is the real constraint. 32 GB machine, ~24 GB usable by the GPU. Weights plus KV cache must fit inside that or inference silently spills to the CPU — and ollama ps still reports 100% GPU while it happens, so the only symptom is a collapse in throughput. The per-token cost cannot be derived reliably: block_count × head_count_kv × (key_length + value_length) is the textbook formula and it gives 34 KiB/token here against a real 98, because this model caches every fourth layer and the runtime adds buffers that scale with context. Acting on the derived figure would have set a window needing 30 GB. So set-context measures instead: it loads the model with a trivial prompt and a large one and divides the change in allocation by the change in tokens, which captures whatever the runtime actually does without needing to know what that is.
